## Release priorities

### Working goal and finish line

Deliver one identified BURST public-testnet release that people can install and
use safely, with initial 1 BRN/hour and the intended whitepaper functionality.
Finish the remaining release blockers against that candidate. Do not restart
completed implementation or validation merely because the broader roadmap is open.

This goal is complete when:

- The final daemon, wallet and node dashboard have recorded source identities,
  artifact hashes and supported installation targets. Their tested combinations
  match the distributed packages.
- P1-P3 establish consumer onboarding, verification, payments, challenge/appeal,
  governance and wallet safety through the apps. Reuse applicable passing stages;
  close only the genuinely missing or invalidated evidence. Resumed journeys do
  not stand in for required fresh onboarding.
- P4 establishes join, authenticated recovery, interruption and reconnect for the
  candidate. Existing optimized cold-retirement evidence remains valid within
  its recorded scope; do not repeat it without an input change or new uncertainty.
- P5 establishes the creator-owned Test identity, private backup confirmation,
  independent installation and a usable distribution handoff. Never distribute
  fixture secrets or treat a generated key as a backed-up key.
- The release states measured operating limits, supported platforms and known
  limitations. No unresolved safety defect or missing required user functionality
  is hidden by a disclaimer. Release gates open only after their evidence passes.

For each remaining action, name the P1-P5 requirement, concrete gap, reusable
evidence and smallest necessary change or check. Inspect terminal results before
calling a recorded job active or restarting it. Documentation changes alone do
not trigger builds.

Mainnet readiness, indefinite-scale storage work and optional visual redesign
remain in the full completion plan. They enter this release only when a concrete
safety, functionality or supported-envelope failure makes them a blocker. This
does not waive whitepaper requirements. An unresolved protocol or product choice
still requires an explicit decision.
