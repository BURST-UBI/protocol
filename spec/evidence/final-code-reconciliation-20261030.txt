## Confirmed findings

### A1 — Saved compiler diagnostics conflict with CI policy

Priority: high for build qualification, not evidence of a critical runtime bug.
.github/workflows/ci.yml:35 sets RUSTFLAGS=-Dwarnings. The current matching
boundary-check4.log contains Rust unused imports/dead-code/private-interface
warnings, plus a future-incompatible recursion-depth diagnostic involving
recover_metadata_from_peers. Applicable Rust warnings become errors under that
policy. Cargo's own manifest notices are a separate category; do not count every
Cargo notice as a Rust compiler error.

The recovery warning points to
node/src/confirmed_replay/snapshot/installed/metadata.rs:598: a function returns
an opaque Send future constructed with Box::pin of another recovery future.
Boxing the value does not necessarily erase its concrete future type. Trace the
reported Send/opaque-type cycle before changing the boundary. Boxing itself is
intentional: RETIREMENT_CAPTURE_DESIGN.md:15181 records a live-restart stack
overflow and the subsequent boxed-recovery restart/cancellation passes. Retain
that allocation boundary; the warning is not grounds to unbox recovery. Do not raise
recursion limits or blanket-allow warnings just to produce a green job. This pass
did not reproduce a runtime failure or run another compiler with changed flags.

Action: classify existing diagnostics into test-only helpers, genuinely unused
code, API visibility and actual type-boundary issues; fix the relevant source,
then run the smallest matching strict build before expensive end-to-end work.
Keep the normal-build receipts for their actual scope. No unused-code deletion
should be inferred solely from a production-profile warning.

### A2 — Retirement catalogue exposes types at inconsistent visibility

Priority: medium API/compile hygiene; high confidence.
node/src/confirmed_replay/retirement/catalogue.rs:48 and:150 expose crate-visible
enums whose Observed variants contain ObservedCatalogue/ObservedRows. Their
implementations in catalogue/observed.rs:7 and:53 are only pub(super). The compiler
reports both as private_interfaces. This remains after the earlier extraction.

Action: align the intended interface visibility or hide the variant representation
behind a private wrapper. Keep observed page fields and checked proof authority
private. This is not evidence that unauthenticated callers can retire data.
Rsnano's private implementation modules and exposed typed interfaces, for example
store_lmdb/src/block_store.rs, illustrate the useful boundary; matching its module
count is irrelevant.

### A3 — Small graph-record encoding helpers have two active owners

Priority: medium drift risk; high confidence, no current byte disagreement found.
The edge function is identical in node/src/graph_storage.rs:31 and
store_lmdb/src/write_batch/auxiliary_cache/trst/graph_delta.rs:6. Both hardcode the
GraphRecord storage prefixes for origin/downstream edges and read their position.
The adjacent set_position match is also duplicated.

Both paths are real. Ordinary economic delta publication delegates to the backend
CAS writer; full graph persistence, legacy handling and replay installation use
other node paths. Do not merge those operations: preserving surviving journal
positions and rebuilding certified replay rows are different contracts.

Action: give the shared record-group/position operations one owner beside
GraphRecord (or an equally narrow existing owner). Preserve exact storage keys
and position semantics. Retain both full and incremental algorithms. Rsnano keeps
block values/serialization with their type owners and database mutations with the
store; it has no equivalent BURST merger graph algorithm to copy wholesale.

### A5 — Two public descriptions still obscure intentionally different APIs

Priority: low documentation/API clarity, not an observed live conflict.

ledger/src/genesis.rs:33 exposes create_genesis_block as a normal genesis builder,
but delegates to legacy_genesis_fixture. The running node and key generator call
configured_genesis_block. The old constructor/hash helper remain exported at the
ledger root and used by historical fixtures. Preserve their bytes and callers,
but label/deprecate the historical entry points so new consumers do not mistake
them for launch configuration. Existing node launch code is already on the right
constructor. Rsnano similarly centralizes network genesis identity in its ledger
constants; it does not justify rewriting BURST's saved fixture hashes.

rpc/src/state.rs:71 still describes its ProcessResult as mirroring node's result.
The internal result, RPC queued/submission state and wallet wire receipt are
intentionally different. Update that description to match the actual semantics;
do not unify their types or equate submission with finality.

## Apparent duplication that should stay

* Full graph publication, incremental CAS writes and certified replay staging
  have different undo/ordering contracts. Only their small record helpers are
  the duplication finding above.
* Backend governance hydration uses a caller-owned pinned reader and a cache
  tagged by transaction generation. Rsnano puts more application work in ledger,
  but a move that loses those guarantees is not simplification.
* Native wallet, dashboard and wallet_core RPC clients share bounded response
  reading. Dashboard retries only read-side admission rejection; wallet does not
  silently retry writes. Their deadlines and signing/journal responsibilities
  differ. Do not combine them into one automatic-retry client.
* Historical genesis fixtures and configured launch identity are intentionally
  distinct. Only their discoverability needs improvement.
* Legacy Bincode handshake/codec and candidate-only LedgerPruner are explicitly
  isolated. No live node/daemon/RPC/network/message consumer was found in the
  searched call sites. Compatibility retention is not an alternate live protocol.
* Commit-reveal is explicitly an experimental transcript with missing membership,
  deadline and recovery guarantees. ThresholdVrf returns Unavailable for both
  generation and verification. No production constructor/caller was found for
  either; do not wire them in as drand fallbacks. Their documented future scope
  is not a demonstrated missing production randomness path.
* Wire version has one source value in types (protocol reexports it); StateBlock,
  ProtocolParams and ShutdownController each have one implementation owner in
  the inspected workspace. Different ProcessResult meanings are not duplicates.

### Real compatibility qualifications

`BurstNode::start()` now rejects enabled public listeners; NodeConfig defaults
include RPC. Existing external embedders using the former convenience behavior
must migrate to `start_with_services(burst_daemon::start_public_services)` or
explicitly disable listeners for core-only operation. Repository applications were
migrated and docs/ARCHITECTURE.md documents the new entry point. This is an
intentional ownership decision, but it is a Rust API behavior change, not a fully
transparent move. No evidence about unknown external consumers is available.

Removed public prototype exports can likewise break external Rust imports even
when no repository runtime caller exists. The shared verification-status response
also changed selection_unavailable_reason from Option<&'static str> to
Option<String>: its JSON shape is preserved, but direct Rust constructors may
need adjustment. Document these changes when preparing release migration notes.

No concrete lost live signing, recovery or governance validation check was
established by this removal review. That conclusion is bounded to the inspected
changes. A1–A5 above still require their recorded dispositions; in particular,
preserve measured recovery boxing, private retirement proof internals and distinct
full/delta/replay persistence semantics. No production source was changed, no new
build was run, nothing was published and no Azure job was started for this review.
