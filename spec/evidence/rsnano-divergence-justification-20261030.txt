# Are BURST's departures from rsnano justified?

Implementation follow-up: [current fix tracker](SIMPLICITY_FIX_TRACKER_20261030.md).
The findings below preserve the pre-fix review; consult the tracker for current status.

Source review, 2026-10-30. Reference: local rsnano commit
`414dd884c162f78f151b9d912a029bbc9a340866`; not latest-upstream advice.
BURST evidence is the current, already modified working tree. No production code
changed and no builds or runtime checks were run for this report.

This complements [the simplicity review](IMPLEMENTATION_SIMPLICITY_REVIEW_20261030.md).
Different is not automatically worse. A departure needs a protocol requirement,
product requirement, measured benefit, or simpler ownership. An explanation
inferred from code is not evidence that the original author made that decision.
This covers the material direct dependency families and architectural departures
inspected below, not every transitive package, platform feature, or supply-chain risk.

runtime. Inventory above was drawn from member manifests as well as root settings;
target-specific consumers were inspected where relevant, not exhaustively enumerated.

## D01 — Custom mnemonic derivation is mislabeled as BIP44

Priority: recovery interoperability and accurate public documentation, before
claiming standard HD-wallet compatibility. This is a live path:
`wallet_core/src/wallet.rs` calls `keypair_from_mnemonic`.

`crypto/src/mnemonic.rs:57` uses the literal `m/44'/9999'/0'/0/0` string as the
HMAC-SHA512 key and the BIP39 seed as its message, taking the first 32 output bytes.
There are no successive child derivations, child indexes, or retained chain code.
This is deterministic BURST-specific derivation, not implementation of that path.

Decision 4.2 selects a BIP44 coin path; it does not authorize replacing the
derivation algorithm with a path-string HMAC. BIP44 specifies a BIP32 hierarchy.
For a standard Ed25519 design, SLIP-0010 supplies a relevant established derivation
scheme, but it supports hardened children only: the existing unhardened suffix
cannot simply be passed through unchanged.

Primary references checked:
[BIP44](https://github.com/bitcoin/bips/blob/master/bip-0044.mediawiki),
[SLIP-0010](https://github.com/satoshilabs/slips/blob/master/slip-0010.md).

This finding does **not** demonstrate key compromise, weak entropy, or a broken
BIP39 library. It demonstrates a mismatch between promised derivation and code.
Rsnano's own deterministic key handling is not a reason to invent an undocumented
BURST variant or to copy Nano recovery rules into BURST.

Smallest safe next step: specify and name the current recovery scheme accurately,
preserve independent known phrase-to-key/address vectors, and determine whether
existing wallets require legacy recovery. If adopting standard HD derivation for
new wallets, use a reviewed implementation with explicit derivation version and
compatible recovery handling. Never silently change the output for old phrases.
Coin-type registration status was not checked here.

## Architectural departures: retain the requirements, simplify their expression

| Departure | Justification judgment | Action |
|---|---|---|
| BRN/TRST state, provenance, expiry/revocation, certified enrollment and governance | Real BURST semantics with no direct Nano substitute | Keep the rules. Shared live/fork economic transitions are good reuse; old local verification and alternate tally APIs are not (S01/S12/S14). |
| Score-sorted square-root gossip rather than randomized selection | No demonstrated need to repeatedly favor the same peers; decision 23.9 follows Nano | S08: reuse bounded subset/random selection after preserving peer eligibility and budgets. No throughput improvement or eclipse exploit is established by this source review. |
| Adaptive difficulty bookkeeping alongside governed work thresholds | No live consumer justifying the extra node bookkeeping found | S07: remove inactive machinery; do not activate a second policy to justify its existence. |
| Raw JSON repeated in signing review vs rsnano typed RPC DTOs | No protocol reason for repeated string contracts | S06: incrementally share typed response contracts while preserving independent signing checks. |
| JSON serialize/reparse per WebSocket subscriber | No identified requirement | S16: route typed existing events and serialize at the boundary; no new event-bus framework needed. |
| Several genesis constructors and simulation rollback APIs | Historical fixtures may explain some copies, but do not justify ambiguous production entry points | S10/S13: isolate simulations and canonicalize launch construction without altering historical fixtures accidentally. |

## Stopping point and priorities

The useful next work is targeted correction, not a wholesale port to rsnano.
First resolve D01's recovery contract, S02/S03 error handling, and S15 unchecked
aggregation. Then remove inactive alternate policy machinery and consolidate
existing parsing, HTTP and event paths. Keep native storage patch qualification
as a distinct release/maintenance obligation; this report does not pass its gates.

Another broad style pass has diminishing value now. Stop before replacing sound
libraries just for parity, writing a universal codec/transport framework, removing
trust-boundary checks as duplicates, or changing consensus and wallet formats to
make the tree resemble Nano. Reopen review when a concrete change or new evidence
provides a specific question. No vulnerability-advisory, license-compliance, or
exhaustive transitive-dependency audit is claimed here.
