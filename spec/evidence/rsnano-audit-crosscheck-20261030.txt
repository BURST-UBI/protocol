## Source evidence and reasoning

### PA06 and FA03: validate before mutation, without overstating equivalence

Rsnano `ledger/src/block_insertion/validation/mod.rs::validate` returns
`BlockInsertInstructions` only after predecessor, signature, pending amount,
work and spend checks. `receive_block_rules.rs` rejects mismatched pending credit.
`ledger/src/ledger.rs::process_batch` only sends successful instructions to the
inserter. `block_inserter.rs` checks whether the account head changed before
writing. These are useful examples of separating validation from application.

BURST already has staged node transitions and stable persistence validation. The
PA06 reproduction shows an engine boundary losing an error, not absence of all
transaction protection. FA03 concerns a caller-provided invalid state and an Err
return after a partial update. There is no evidence these behaviors were chosen
as protocol rules, but no valid ledger attack was demonstrated either. Make the
small local fixes; do not introduce broad extra staging layers throughout BURST.

Sources: [validation](https://github.com/rsnano-node/rsnano-node/blob/414dd884c162f78f151b9d912a029bbc9a340866/ledger/src/block_insertion/validation/mod.rs),
[receive rules](https://github.com/rsnano-node/rsnano-node/blob/414dd884c162f78f151b9d912a029bbc9a340866/ledger/src/block_insertion/validation/receive_block_rules.rs),
[inserter](https://github.com/rsnano-node/rsnano-node/blob/414dd884c162f78f151b9d912a029bbc9a340866/ledger/src/block_insertion/block_inserter.rs).

### FA01: same unbounded local-file pattern

Rsnano `cli/src/cli/commands/wallets/import_keys.rs::import_keys` opens the path,
reads it into a String, then calls wallet import/replace. `LmdbWalletStore::new_from_json`
parses a serde_json Value and decodes wallet entries. Its variable account-count
backup format differs from BURST's fixed-size encrypted seed format: equal byte
limits are not implied. The shared pre-parse allocation pattern is directly
visible; no Rsnano OOM test was run.

BURST's 1-MiB ignored metadata test demonstrates acceptance, not a crash. There
was no evidence supporting higher urgency than local availability hardening.
A user-selected file can still be hostile, so bounded reading is useful despite
Rsnano sharing the assumption. Unknown JSON fields can be intentionally tolerated
for compatibility; rejecting every unknown field is unnecessary to impose a cap.

Sources: [CLI import](https://github.com/rsnano-node/rsnano-node/blob/414dd884c162f78f151b9d912a029bbc9a340866/cli/src/cli/commands/wallets/import_keys.rs),
[wallet store](https://github.com/rsnano-node/rsnano-node/blob/414dd884c162f78f151b9d912a029bbc9a340866/store_lmdb/src/wallet_store.rs).

### FA02: key scattering is not guaranteed wiping

Rsnano `types/src/raw_key.rs` uses `u256_struct!(RawKey)`; the macro derives Copy
and contains a [u8;32]. `RawKey::encrypt/decrypt` creates another raw buffer.
`store_lmdb/src/fan.rs` distributes fragments but `value` reconstructs a copy.
PrivateKey wraps dalek's SigningKey, which is a separate boundary: this review
does not claim all dalek-managed keys lack wiping. It establishes only that raw
copies and passwords are not comprehensively erased in the inspected application
paths. BURST should minimize its own temporary lifetime without treating this
as a cryptographic algorithm defect.

Sources: [RawKey](https://github.com/rsnano-node/rsnano-node/blob/414dd884c162f78f151b9d912a029bbc9a340866/types/src/raw_key.rs),
[wrapper macro](https://github.com/rsnano-node/rsnano-node/blob/414dd884c162f78f151b9d912a029bbc9a340866/types/src/u256_struct.rs),
[Fan](https://github.com/rsnano-node/rsnano-node/blob/414dd884c162f78f151b9d912a029bbc9a340866/store_lmdb/src/fan.rs).

### FA04: explicit simple REST design; TLS restriction was not specified

BURST IMPLEMENTATION_DECISIONS 22.1 selects a public IPFS/web directory; 22.2
selects simple GET membership queries instead of challenge-response/signed
responses; 22.3 selects live queries. `groups/src/lib.rs` explicitly describes
HTTP endpoints and an off-chain application trust overlay. Client, registry and
wallet validation accept HTTP(S). docs/PRIVACY.md already explains that remote
plain HTTP is unencrypted for node connections, though it does not specifically
explain group membership disclosure.

These records establish the simple API choice. They do not prove the owner
separately evaluated every remote plaintext risk. No document found establishes
HTTPS-only membership as a requirement. Therefore the original unconditional
“require HTTPS” recommendation was too strong as a defect fix. Document the group
query/response trust boundary and prefer HTTPS; making remote HTTP impossible
would be a policy change. Directory retrieval and membership queries have different
disclosures and should not be conflated. Interception can still influence a user's
optional acceptance policy even though it cannot grant consensus voting weight.

Rsnano's local RPC URL policy is only context, not an equivalent group service:
[RPC client](https://github.com/rsnano-node/rsnano-node/blob/414dd884c162f78f151b9d912a029bbc9a340866/rpc/client/src/lib.rs),
[RPC defaults](https://github.com/rsnano-node/rsnano-node/blob/414dd884c162f78f151b9d912a029bbc9a340866/rpc/server/src/config.rs).

## Carried findings and other conclusions

* PA03 private RPC priority remains intentional; Rsnano's local source receives
  its configured local queue priority. No extra public-ingress architecture is
  needed for the current private-RPC deployment model.
* PA01 checked governance widths, PA02 full-width balance scheduling, PA04 wallet
  accounting and PA05 keystore profile validation remain justified fixes. Rsnano
  has no equivalent BURST governance or BRN model; its Amount stores u128. Human
  display conversion is not a reason to clamp scheduler balance keys.
* Q01 constitutional thresholds and Q02 independent custodian authority remain
  BURST model/documentation questions. Nano has no matching governance or guardian
  authority whose behavior can settle them. Do not add guardian signing merely
  to make local metadata look like a completed consensus feature.
* PD01's correction remains justified: Nano-style pruning is not a guarantee of
  bounded total state, and BURST retains additional provenance/revocation history.
  No reason found to remove the production retirement gate.
* Dependency advisories are package/version/path questions, not choices endorsed
  by another project. Existing disputed block-buffer classification and unresolved
  transitive reachability stay unchanged. No second advisory scan was needed.
* Action tags also occur in Rsnano's
  [release workflow](https://github.com/rsnano-node/rsnano-node/blob/414dd884c162f78f151b9d912a029bbc9a340866/.github/workflows/docker_release.yml).
  Shared practice does not authenticate a compromised publisher. No equivalence
  between its Docker release and BURST's desktop installer signing is claimed.
